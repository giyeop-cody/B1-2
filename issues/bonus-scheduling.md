# [Analysis] 로그와 OS 관측으로 확인한 스케줄링 특성

## 1. 로그 관찰 개요

2026-10-07 OrbStack에서 정상 설정(CPU_MAX_OCCUPY=50)으로 별도 실행하고
30초 램프업 후 12초간 CPU 시간 증분을 측정했다.
[측정 원본](../evidence/40-scheduling-probe.txt)과 [전체 로그](../evidence/phase2.log)를 참조한다.

## 2. 증거 자료

- 스레드 정책: SCHED_OTHER, 우선순위 0, nice=10.
- /proc 기반 OS 프로세스 CPU: 28틱 / 12.004초, **2.33%**.
- 단일 busy-loop 대조군: **100.17%**. 표본·시간 측정의 오차가 포함된다.
- 워커 syscall 표본: 270=pselect6. 자발적 컨텍스트 스위치가 비자발적 스위치보다 많다.
- 앱 로그: 내부 Load 상승, 50% peak, cooldown 패턴. OS 사용률과 수치가 다르다.

## 3. 패턴 분석 및 결론

이번 워커는 대부분 스스로 대기하며 간헐적으로 실행된다. 앱 내부 Load는 OS CPU 사용률의
직접 측정값으로 볼 수 없다. nice 값과 SCHED_OTHER는 관측했지만,
로그의 교차 출력만으로 Round-Robin·FCFS·Priority 중 하나를 확정할 수 없다.
명시적인 SCHED_RR 정책도 관측되지 않았다. 커널의 구체적 구현 알고리즘은
별도 커널 설정·소스 검증 없이 CFS로 단정하지 않는다.

## 4. 장단점과 서비스 적용

주기적으로 대기하는 앱의 동작은 CPU 소모를 낮출 수 있으나 깨어나는 간격만큼
응답 지연이 생길 수 있다. 이번 측정으로 웹 서비스 지연이나 배치 처리량의
우열까지 확인하지 않았다. 보너스의 알고리즘 분류 요구는 **판정 유보**로 기록한다.
